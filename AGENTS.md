# AGENTS.md

Guidance for AI coding agents and for humans working in this repository. `CLAUDE.md` imports this file.

## Build, Lint, Test Commands

```bash
pnpm install --frozen-lockfile   # install dependencies
pnpm run build                   # build all packages (turbo)
pnpm run test                    # test all packages (turbo, runs vitest)
pnpm run test:packed             # pack the npm packages, install them outside the workspace, run `easytestdata ui`
pnpm run test:qbo-live           # load, roll back and purge in a real sandbox (see CONTRIBUTING.md)
pnpm run check                   # everything CI checks: lint, format, build, packed install, tests, audit
pnpm run lint                    # migration sequence check + eslint across all packages
pnpm run format                  # prettier write
pnpm run format:check            # prettier check (CI)

# Single package
pnpm --filter @easytestdata/core run test
pnpm --filter @easytestdata/qbo-client run test
pnpm --filter @easytestdata/server run test
pnpm --filter easytestdata run test          # cli package

# Watch mode (any package)
pnpm --filter @easytestdata/core run test:watch

# Development and running
pnpm run dev                                    # server in local mode on :28080 + Vite web app on :5173
node packages/cli/bin/easytestdata.js ui        # the app as users run it (npx easytestdata ui)
pnpm --filter @easytestdata/server run migrate  # run migrations (no DATABASE_URL: the local PGlite database)
pnpm run start                                  # server with the root .env (Cloud when it sets DATABASE_URL)
pnpm --filter @easytestdata/marketing run build # the static marketing site (APP_URL at build time)
```

Runtime baseline: the project builds, tests, releases and deploys on **Node.js 24** (`.nvmrc`, CI, CloudPanel); the published packages support **Node.js 22.13+** (`engines.node >=22.13.0`, checked by CI's `node-22` job: the CLI's commander/inquirer and the dev tools need it; it also covers `node --env-file-if-exists`). `pnpm run engines:check` (part of `lint`) keeps every package's `engines`, the preinstall guard and every locked dependency in line with it.

Nothing else is needed to develop: no Docker and no Postgres server. `pnpm run dev` runs
the server in local mode (embedded PGlite, data in `~/.easytestdata`, `LOCAL_PUBLIC_URL=http://localhost:5173`
so the Vite dev server, which proxies `/api`, is the public address) and needs no `.env`. Tests
mock the database or use PGlite. For Cloud-parity work, set `DEPLOYMENT=cloud` and `DATABASE_URL`
(plus the secrets) in `.env` and use `pnpm run start`.

Production (EasyTestData Cloud): one Node process, `node --env-file=.env packages/server/src/start.js`,
on a CloudPanel VM behind its nginx with Cloudflare in front (app port in 28000-28999), Postgres
on the VM. See `docs/deploy-cloudpanel.md`. The marketing site is static on Cloudflare Pages
(`docs/cloudflare-pages.md`); the server serves only the app. Local mode: `docs/run-locally.md`.

## Monorepo Architecture

pnpm workspaces + Turborepo. Core package dependency graph:

```
@easytestdata/core          (no deps — pure generation engine)
       ↓
@easytestdata/qbo-client    (depends on core)
       ↓
@easytestdata/server         (depends on core + qbo-client + shared; ships the built web app)
easytestdata (cli)           (depends on core + qbo-client + server; only `ui` loads the server)
@easytestdata/shared         (Zod schemas, constants, typed API client and hooks)
@easytestdata/ui             (shared React components)
@easytestdata/web            (depends on shared + ui, consumes the server API)
@easytestdata/marketing      (static site; bundles core for the browser playground)
examples/                    (private workspace package; its tests run the examples)
```

Backend/shared packages use **ES modules** and **vitest**. The web package is **React + TypeScript + Vite**.

Published to npm (Changesets, one version, first release v0.1.0): `easytestdata` (CLI),
`@easytestdata/core`, `@easytestdata/qbo-client`, `@easytestdata/shared`, `@easytestdata/server`.
Everything else is private.

Licensing: every package is **Apache-2.0** (root `LICENSE` + `NOTICE`). `packages/web` serves both Cloud and local mode; the difference is a product choice, not a license boundary. The npm-published packages carry copies of `LICENSE` and `NOTICE`; keep them in sync with the root. Package `NOTICE` copies omit the shadcn/ui paragraph, which only applies to `packages/ui`, except the server's: it ships the built web app (`web-dist`), so its `NOTICE` keeps the paragraph and points to its own copy of `packages/ui/THIRD_PARTY_NOTICES.md`.

## Two modes: Cloud and local

`config.deployment` is `DEPLOYMENT` (`cloud` | `local`), or when unset `cloud` if `DATABASE_URL`
is set, else `local`. `startup-checks.js` refuses an implicit local mode when `NODE_ENV=production`,
`TRUST_PROXY` or `APP_URL` is set (a Cloud server that lost `DATABASE_URL` must not become the
no-login app), and any other `DEPLOYMENT` value.

|             | Cloud                                                     | Local (`npx easytestdata ui`)                                                                  |
| ----------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Database    | Postgres at `DATABASE_URL` (`pg`)                         | PGlite in `<dataDir>/db` (always, even if `DATABASE_URL` is set)                               |
| Listens on  | `HOST` (default `0.0.0.0`) : `PORT` (CloudPanel app port) | `127.0.0.1` only : `PORT` (default `28080`); no option to widen                                |
| Sign-in     | Google, GitHub, Intuit OAuth; JWT sessions                | none: `authenticate` sets the built-in local user and team                                     |
| Limits      | `DEPLOYMENT_LIMITS.cloud`                                 | `DEPLOYMENT_LIMITS.local` (all `-1`)                                                           |
| Secrets     | `JWT_SECRET`, `TOKEN_ENCRYPTION_KEY` from the environment | generated into `<dataDir>/secret.key` (0600) unless set in env                                 |
| Intuit keys | `QBO_CLIENT_ID` / `QBO_CLIENT_SECRET` only                | setup screen (`/setup`, `PUT /api/v1/setup/qbo`), stored encrypted in `app_settings`; env wins |
| Hidden      | —                                                         | teams, invites, admin area, sign-in routes, rate limiter, CORS                                 |

`dataDir` is `EASYTESTDATA_DATA_DIR` or `~/.easytestdata` (`--data-dir` on `ui`), created 0700;
downloads go to `<dataDir>/exports`. The app URL is `http://localhost:<port>`, and the Intuit
redirect URI is `<app URL>/api/v1/connections/callback`. Local mode is for one person on one
machine and must never be put behind a reverse proxy or exposed.

## Package Responsibilities

### `packages/core` — Synthetic Data Engine

Deterministic financial data generation. Zero runtime dependencies; runs in Node and browsers.

- `generate(opts)` → the entry point (CLI, server, playground, README): resolves template, preset,
  period, and amounts (`"1.5M"`), with precedence explicit option > preset > default
- Lower-level flow it wraps: `applyScenarioPreset` → `normalizeRequest` → `resolveConfig` →
  `buildSyntheticPlan(input, config, { seed })`
- `exportToJson()` / `exportToCsv()` → `exportToCsv` returns one snake_case table per record type,
  including `invoice_lines`, `bill_lines`, and friends
- Same seed + same explicit dates ⇒ byte-identical output. Without dates the period is the 12 full
  months before today.
- Parties (customers, vendors, employees) are realistic, locale-aware objects
  (`{ id, name, email, phone, address }`), unique across the plan; unknown template/preset ids throw.
- Generation is bounded: every ratio has a range in `RATIO_BOUNDS` (next to `RATIOS`; user
  overrides outside it throw, template values are clamped), a period spans at most `MAX_MONTHS`
  (120) even with explicit dates, a plan has at most `MAX_EMPLOYEES` (50) employees (the server and the
  web form refuse more rather than let core clamp), and months x customers <= 5000. The server validates all of
  this in `normalizeScenarioConfig` (400) before building any plan.

Templates (8 industries) and presets (8 scenarios) live in `src/templates/`. The first ```js block
of `packages/core/README.md`and of the root`README.md`run in`tests/readme.test.js`, so keep
them working.

### `packages/qbo-client` — QBO API Client

- `QboClient` — HTTP wrapper with OAuth token refresh, rate limiting (450 req/61s), and retry (429 for every request; 500/503 only for GETs, so a write QBO may have committed is never replayed). **Cancellation rule:** a long operation's client is built with its `signal` (`new QboClient({ ..., signal })`; the server's `buildLockedQboClient(conn, credentials, { signal })` for load, purge and rollback jobs, the CLI's Ctrl+C for `load`/`purge`): once it aborts, the client starts no request (retries and rate-limit waits included; `QboRequestCancelledError`), however deep in a helper the call is. A request already sent finishes, since QBO may have applied it. The helpers also take the signal (`queryAll` per page, the batch helpers per chunk, `inactivate*`, purge/rollback/load per step) so they stop cleanly between steps; `tests/cancel-at-each-step.test.js` aborts purge and rollback at every QBO call and checks that no further call starts
- `batchCreate/batchDelete/batchUpdate` — chunked operations (30 items per batch, 2 in flight). On abort they start no new chunk, drain the in-flight ones, and throw an error carrying `partial` (what was created/deleted); `batchCreate` reports each batch through `onCreated` as soon as it lands
- `loadPlanIntoQbo(client, plan, config, emit, signal)` — 11-phase orchestrator that creates accounts, master data, service items, then all transaction types in dependency order. Existing customers/vendors/employees are reused only when they carry the plan tag (the lookups include inactive records, so ones made inactive by Remove test data or a rollback are reactivated); a generated party whose display name is taken by an untagged record, active or inactive, is created as `Name (TAG)` (then `Name (TAG 2)`, ...), and a later load finds and reuses that tagged record. Service items follow the same rule with their `Description` tag: an untagged item holding the name is never reused or reactivated (`ensureServiceItem` refuses it too). Accounts are reactivated by name, which is safe because every account the load creates is named `TAG ...` (except QBO's standard `Undeposited Funds`). A party QBO refuses to create is listed in the load's `failures` with QBO's reason. The ledger is written per batch and parallel phases settle fully before a failure is rethrown, so `err.ledger` covers every record that exists when a load is cancelled or fails. The ledger includes the accounts, customers, vendors, employees and service items the load created or reactivated, not only transactions
- `generated-identity.js` — `isGeneratedRecord(entityName, record, tag)`, the one "did we generate this?" rule, used by load reuse/reactivation, Remove test data (generated mode) and `ensureServiceItem` (a rollback acts on its ledger's ids instead). Transactions: `PrivateNote` or `DocNumber` starts with the tag. Master data: its tag field (`MASTER_DATA_TAG_FIELDS`: customer `Notes`, vendor `AcctNum`, employee `EmployeeNumber`, item `Description`) starts with the tag; a tag field holding anything else, or nothing, is not ours, whatever the name. Names are never looked at, so a user's "Amy's Bird Sanctuary" is never taken for tag `AMY`, nor "A-1 Plumbing" for `A`. `tagMatches` is token-aware (`EZTDX` is not `EZTD`); nothing else in the package matches tags (`tests/generated-identity.test.js` is the decision table)
- `purgeTransactions(client, options, emit, signal)` — ordered deletion with tag-based filtering (mode: "generated" or "all")
- `rollbackLoad(client, ledger, emit, signal, { keepMasterData })` — deletes the ledger's transactions in reverse dependency order, then makes its items, employees, vendors and customers inactive (QBO cannot delete them; purge inactivates them the same way). Accounts stay in the ledger but are never inactivated, as purge leaves them: QBO may refuse (a balance, an item posting to one) and the rollback could then never succeed. Records already gone or inactive are skipped, so a failed rollback can be retried; the report carries `totalDeleted`, `totalInactivated`, and `keptMasterData` plus a `note` when anything was kept ("QuickBooks accounts are left in place, as "Remove test data" does (N kept)."), so a ledger of only accounts rolls back successfully with that note. With `keepMasterData` it deletes only the transactions; the worker passes it when a later load into the same sandbox (`laterLoadMayUseMasterData`: any team's connection with the same `realm_id`, created after the rolled-back load, status running, cancelling, completed, failed or failed_with_orphans) may be using that master data, and the note points to Remove test data
- `qbo-repository.js` — entity lookup/creation helpers, paginated queries (re-exports `tagMatches`, `MASTER_DATA_TAG_FIELDS` and `partyTag` from `generated-identity.js`)

### `packages/cli` — CLI Tool

Commander-based CLI (`easytestdata`). Commands: `generate`, `plan`, `load`, `purge`, `auth`, `templates`, `presets`, `ui` (`--scenario` and `--profit`). Config stored in `.easytestdata.json` with named QBO connections (`saveConfig` makes the file 0600, an existing one too, before writing tokens). `ui` (`--port`, default 28080; `--data-dir`; `--no-open`) imports `@easytestdata/server/local` only when it runs and calls `startLocalServer`, which forces `DEPLOYMENT=local`, drops an inherited `DATABASE_URL`, defaults `NODE_ENV=production` and `LOG_LEVEL=warn` (a terminal app: warnings and errors only, no per-request lines; `LOG_LEVEL` overrides), starts the server and opens the browser; Ctrl+C stops it cleanly, a second signal exits at once.

### `packages/shared` — Shared Schemas, Constants and API Client

Single source of truth for Zod validation schemas consumed by both `packages/server` and `packages/web`. Entry points:

- `@easytestdata/shared/schemas` — all Zod request schemas (auth, jobs, teams, etc.)
- `@easytestdata/shared/constants` — shared constants, including `DEPLOYMENT_LIMITS` (`cloud` abuse limits and the unlimited `local` set) and `limitExceededMessage()`
- `./api-client`, `./api-hooks`, `./types` — the typed fetch client (sends `X-EasyTestData: 1` on every request, `CLIENT_HEADERS`), react-query hooks (`@tanstack/react-query` is an optional peer, so the server and CLI don't pull React) and shared types. These are TypeScript sources for the workspace (web, ui) only: the published package ships just the JavaScript entry points `.`, `./schemas`, `./constants` and `./query-keys`, each with a hand-written `.d.ts` next to it named by a `types` condition (`publishConfig.exports` and `files` in its `package.json`); keep a `.d.ts` in step when its `.js` changes. `scripts/shared-entry-points.mjs` is the rule (JavaScript that ships, with declarations, no TypeScript source): `test:packed` applies it to the real tarball, and `packages/cli/tests/packed-shared-entry-points.test.js` applies it (plus a check that each `.d.ts` declares every name its `.js` exports) on every test run

### `packages/server` — API server (Cloud and local)

Express API with an in-process job runner, serving the built web app. One process: all
short-lived state lives in memory.

**Backend** (`src/`):

- `start.js` — `bootstrap()`: startup checks (exit on fatal), local secrets (local), the single-server lock, migrations, local identity (local), job runner, HTTP server; `close()` stops HTTP, then the runner, then the database, then releases the lock; every step runs even when an earlier one fails (the first error is rethrown), so the database is closed before the lock goes. One server per database: before migrating or recovering jobs, local mode creates `<dataDir>/server.lock` (0600, the pid, written to a temp file and hard-linked into place; `local/instance-lock.js`: a lock whose pid is gone is taken over by one starter at a time, which first creates the guard `server.lock.takeover` the same atomic way, re-checks the lock under it, then replaces it; a starter that finds the guard refuses, so of any number of starters racing for a stale lock exactly one wins and a live lock is never moved; one without a readable pid counts as held for 10 s; a directly run local `migrate` takes the same lock. Accepted residual: a starter killed inside the takeover leaves `server.lock.takeover`, and the next start that finds a stale lock refuses with "An earlier start was interrupted and left <file>. If EasyTestData is not running, delete that file and try again." (prefixed with "Another copy of EasyTestData may be starting with this data folder (pid N). Or an earlier start …" while the guard's pid is alive, which is also what a reused pid looks like). A pid file was kept over an OS lock because Node has no portable one without dependencies: `flock` is not exposed, abstract sockets are Linux-only, and a socket file on macOS goes stale like a pid file) and Cloud takes a session `pg_try_advisory_lock` on its own keep-alive connection (`lockDatabase()` / `SERVER_LOCK_KEY` in `db/pool.js`, distinct from migrate.js's `MIGRATION_LOCK_KEY`; if that connection errors or ends, the server runs `close()` and exits 1); a second server exits with "EasyTestData is already running with this data folder (pid N)…" / "Another EasyTestData server is already running against this database." and touches nothing. A startup failure after the lock stops what it started, closes the database (even if stopping the runner fails) and releases the lock (always, even if that cleanup throws; the startup error is rethrown); `close()` also releases it in a `finally`. `handleShutdownSignals`: the first SIGTERM/SIGINT closes cleanly, a second exits 1 at once.
- `startup-checks.js` — refuses unsafe config: unknown `DEPLOYMENT`, implicit local with production signals, and (Cloud with `NODE_ENV=production`) missing `DATABASE_URL`/`JWT_SECRET`/`TOKEN_ENCRYPTION_KEY`/`APP_URL`; a default/short (<32) `JWT_SECRET` or non-hex `TOKEN_ENCRYPTION_KEY` is fatal there and, whenever set, in local mode. Warns about missing OAuth keys and a non-loopback `LOCAL_PUBLIC_URL`.
- `server.js` — `createApp()`: local guards first (local), trust proxy, security headers (CSP in production, also local mode; `img-src` allows Google/GitHub avatar hosts), CORS + rate limiter + passport (Cloud only), request id, logging, `/health`, `/api/v1/config/public`, routes (`/auth`, `/connections`, `/jobs`, `/templates`; Cloud: `/teams`, `/admin`; local: `/setup`), then the SPA. Public `GET /health` runs `SELECT 1` and returns only `{status}` (200 `ok`, 503 `error`); the admin Overview (`GET /api/v1/admin/dashboard`) shows uptime, memory and jobs by status.
- `frontend.js` — serves the SPA (`/assets` immutable, other static files, then `index.html` for every non-`/api/` path). No marketing pages.
- `local/guards.js` — `localRequestGuards`: 403 unless `Host` is `localhost:<port>`, `127.0.0.1:<port>` or the public URL's host (DNS rebinding); 403 on any forwarding header (`Forwarded`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Real-IP`); for non-GET/HEAD/OPTIONS, 403 on a foreign `Origin` and without `X-EasyTestData: 1` (a cross-site page cannot add it without a CORS preflight, which local mode never grants). No endpoint changes data on a GET except the Intuit OAuth callback, which checks its signed, browser-bound, single-use state; `GET /connections/authorize` allocates an in-memory OAuth state, so it gets the Origin and header checks too (`STATEFUL_GETS`, matched on the normalized path).
- `local/secrets.js` (`ensureLocalSecrets`: data dir 0700, `secret.key` 0600 written atomically, JWT secret derived from it; a damaged key is refused, never replaced), `local/identity.js` (`ensureLocalIdentity` / `getLocalIdentity`: the one local user and team), `local/start-local.js` (`startLocalServer`, used by the CLI).
- `routes/` — auth, connections, jobs, teams, templates, setup (local), admin (`dashboard`, `users`, `jobs`, `connections`)
- `middleware/auth.js` — local mode: `req.user` is the local user (role `owner`, not admin). Cloud: JWT only (`verifyAccessToken`). The user status, `is_admin`, `session_version` and team memberships are read from the DB on every request, so suspension, sign-out everywhere and membership changes apply on the next request; a token whose `sv` claim is behind `users.session_version` gets 401 `SESSION_REVOKED`, and a token for a team the user left gets 401 `TEAM_MEMBERSHIP_REVOKED` so the client refreshes into a valid team. `requireRole` / `requireTeamManager` (owner/admin) gate connection delete (409 while a pending/running/cancelling job uses the connection or its lock is held); routes check the role for invite management and purge `mode=all` (also loads with `purgeMode: "all"`).
- `middleware/rate-limiter.js` — Cloud only. Per client IP, fixed windows in process memory (`rateLimits` in `state/memory.js`): a strict auth bucket (20/15 min) on `/refresh` and `/oauth/exchange` (the routes that take a one-time credential) and a general bucket (300/60 s). No per-user tier. Sensitive paths are matched on the normalized path (`http/route-path.js`: decoded, lowercased, trailing/repeated slashes stripped) because Express routes `/auth/REFRESH/` to the same handler; the normalizer may over-match but never under-matches a path Express routes (`rate-limiter.test.js` checks this empirically). The list is expanded via `authRoutePaths()` under `AUTH_ROUTE_PREFIXES` (`/api/v1/auth`). Local mode has no limiter (every request is 127.0.0.1, so a foreign page could drain the one bucket).
- `state/memory.js` — `createTtlStore()` (Map with per-entry expiry; `take()` reads and deletes in one step) and `createFixedWindowLimiter()`; the instances `oauthStates`, `oauthCodes` and `rateLimits`. A restart forgets them (in-flight sign-ins restart; limits reset).
- `workers/runner.js` — `startJobRunner()`: first `recoverInterruptedJobs()` (jobs left `running` → `failed` with "Interrupted by a server restart. Records it created may remain; use "Remove test data" to delete them.", `cancelling` → `cancelled` with "Cancelled while the server restarted." and the same Remove test data hint, since the ledger lived only in memory), then polls `pending` rows every second (and when `notifyJobQueued()` wakes it) in two lanes: QBO (`load`, `purge`, `rollback`; `QBO_WORKER_CONCURRENCY`, default 6) and file jobs (`generate`, `export`; 5). An in-memory in-flight map prevents double dispatch; `processJob`'s `UPDATE ... WHERE status = 'pending'` claim stays the atomic guard. Maintenance on `setInterval`: daily QBO token refresh (`token-refresh.js`: for connections idle 86–100 days it forces a refresh with Intuit under the connection lock; a rotated token is persisted through the compare-and-swap and confirmed, an unrotated one just advances `last_used_at`) and 6-hourly export-artifact cleanup (`JOB_ARTIFACT_TTL_DAYS`, default 7). Both also run once at startup after recovery, in the background (dispatch does not wait for them; a failure is logged), so frequent restarts never starve them. `stop()` stops claiming, aborts the maintenance signal (`refreshExpiringTokens({ signal })` then refreshes no further connection and ends its busy back-off; the Intuit call in flight finishes and its rotated token is persisted), gives maintenance and running jobs up to 15 s together, warns if maintenance is still running (a token it rotates from then on is not stored: the persist fails once the database is closed and is logged as a failed refresh), then aborts the jobs with `JobShutdownError` ("Interrupted by a server shutdown.") and waits until their work has really stopped (ledgers and tokens persisted).
- `workers/index.js` — `processJob({ jobId, kind })`: every job runs under a hard timeout (`QBO_JOB_TIMEOUT_MINUTES` / `LOCAL_JOB_TIMEOUT_MINUTES`, aborts via `AbortSignal`, no retry); after the abort it waits up to `JOB_TIMEOUT_GRACE_SECONDS` (default 60) for the job's own error path to persist its ledger and release the connection lock before failing it. A load that only stops after the grace still gets its ledger: the timed-out row is flagged (`result = {"timedOut": true}`) and that one late ledger write may upgrade it from `failed` to `failed_with_orphans`, whichever terminal path carries the ledger (`markJobFailed`'s `upgradeTimedOut`, and `markJobCancelled` for a cancel whose batches drained past the grace, or a load that finished while cancelling); the lock is released when the work really stops. A `generate`/`export` job writes its files under the same signal: a timeout or cancel stops the writing, removes the job's files (partial ones too) and ends the job through the normal timeout/cancel path, never `completed`. A load's plan file (JSON) is written after its QBO work under the same signal too, but an abort there only drops the file: the finished load still completes with its ledger and `artifactError`. Only a `running` job completes: work that finishes while the job is `cancelling` ends as `cancelled` (or `failed_with_orphans` with the ledger for a load, so it can be rolled back) and counts no usage. Completed rollbacks count toward monthly usage like every other completed job. `abortAndDrainJobs(reason)` is the shutdown path.
- `db/pool.js` — one adapter for both backends: `query(text, params)` and `transaction(fn)` (plus `execScript`, `withConnection` for migrations, `closeDatabase`, and `rollback(value)`: return it from `fn` to roll back and still resolve to `value`). `pg.Pool` for Cloud, PGlite for local (creates the data dir 0700 before opening it; one connection: callers take turns and a transaction holds the turn, so others wait and never see uncommitted rows).
- `db/migrations/` + `db/migrate.js` — the schema is one baseline, `001_initial_schema.sql`; new changes go in `002_*.sql`, ... (never edit an applied file; `pnpm run migrations:check` checks the sequence). On pg the runner takes an advisory lock and applies each file in a transaction; on PGlite it runs whole scripts. A database whose `_migrations` records a name with no file on disk was built by another version and is refused: recreate it.
- `services/connection-lock.js` — the in-process per-connection lock (a Map; `acquireConnectionLock(id, { waitMs })` retries while held and throws `ConnectionLockBusyError`; holders release in `finally`, no TTL or heartbeat). All QBO-token-refreshing paths go through it; build clients from rows read under the lock, and persist refreshed tokens with the compare-and-swap guard that advances after successful writes.
- `services/app-settings.js` — `getQboCredentials()` (env first; local mode falls back to keys saved by the setup screen, encrypted with `TOKEN_ENCRYPTION_KEY`, and warns once per process when they no longer decrypt; Cloud reads the env only), `saveQboCredentials()`, `qboNotConfiguredError()` (503).
- `services/connection-guard.js` — the connection-state rule (see **Connection state** under Key Patterns): `lockTeam`, `lockConnection`, `lockRealmConnection`, `lockConnectingMember`, `hasActiveJob`, `requireUsableConnection`.
- `services/job-enqueue.js` — `insertLimitedJob({ teamId, connectionId, type, config, createdBy, parentJobId, check })`, the only place a job row is inserted: one transaction that locks the team row and the job's connection row (connection guard), refuses a missing (404) or disconnected (409) connection, runs the route's `check` under those locks, applies the monthly load limit to a `load` (the team row lock means concurrent requests cannot both pass the count) and inserts; the one-active-QBO-job index → 409. Used by `POST /jobs`, rollback, connection purge and the admin retry; `services/limits.js` — `getLimits()`, `getMonthlyUsage()`, `enforceJobCreationLimits()`.
- `services/scenario-config.js` — `normalizeScenarioConfig` resolves a posted/stored config like core's `generate()`: explicit value > scenario preset > default, including the period (explicit `months` or both dates > the preset's own `months`, e.g. quick-demo = 3 > 12)
- `auth/passport-setup.js` — Google, GitHub and Intuit OAuth strategies (the only sign-in methods; Cloud only)
- `auth/passport-intuit-sso.js` — Custom Intuit OpenID Connect strategy with sandbox/production userinfo URL support. When userinfo fails it falls back to the id_token of that request's token exchange (passed through passport-oauth2's verify `params`); nothing about a login is stored on the shared strategy instance.
- `config.js` — central config (`deployment`, `port`, `host`, `dataDir`, `appUrl`, `marketingUrl`, `jobs`, `rateLimit`, `adminEmails`); `config.limits` holds the per-deployment limits

## Key Patterns

- **Transactions**: every database transaction uses `transaction(fn)` from `db/pool.js`. Inside `fn`, use only the `client` it receives and pass it to helpers (for example `setActiveTeam(userId, teamId, client)`); calling module-level `query()`, `execScript()` or `withConnection()` inside it, nesting `transaction()`, or using the client after the transaction ended throws, so mistakes fail loudly instead of deadlocking PGlite.
- **Multi-tenancy**: tenant tables have a `team_id` FK; every query filters by `req.user.teamId`
- **Job config snapshot**: `POST /jobs` takes `{ type, connectionId?, templateId, config }` (`POST /jobs/estimate` takes `{ templateId, config }` and returns `{ estimatedEntities, metrics, limit }`), and the normalized config is copied into `jobs.config` JSONB at creation time so it is fixed for the run; it includes a `seed` fixed at creation, so the estimate, the worker and an admin retry build the same plan (the job sheet's Re-run drops the seed and draws fresh data). The API also accepts an explicit `config.seed`: a new load posted with an earlier load's seed is a deliberate second copy, not a replay, and is the caller's responsibility (only the admin retry is guarded by `refuseReplayOverOrphans`). The `jobs` table is also the queue.
- **Connection state** (`services/connection-guard.js`): every write that depends on a `qbo_connections` row's state runs in `transaction()` and locks, in this order, the team row, then the connection row (`SELECT ... FOR NO KEY UPDATE`), then (when it acts for a user) the user's membership row (`FOR SHARE OF tm`; the users row is read for suspension, never locked), and only then checks the state and writes. The paths: storing or reconnecting a sandbox at the OAuth callback (`storeConnection`: membership, suspension and the connection limit are checked there, after the token exchange, so a member removed or suspended meanwhile either waits for the store or makes it refuse with `not_team_member`), disconnecting (team and admin, `connection-disconnect.js`) and inserting any job that uses a connection (`insertLimitedJob`: `POST /jobs` load/purge, `POST /connections/:id/purge`, rollback, admin retry). So a disconnect and a job insert on one sandbox never both succeed, and the fixed order cannot deadlock. The OAuth callback also runs a cheap unlocked membership check before the Intuit token exchange, so a user who left the team is refused without spending one; the check under the locks is what decides. Single-statement writes that decide in their own `WHERE` (the token compare-and-swap, `last_used_at` stamps) need no lock. `tests/connection-guard-pglite.test.js` checks each path and that jobs are inserted, and sandboxes connected or disconnected, nowhere else.
- **Row-lock order** (Cloud Postgres; PGlite has one connection, so it cannot deadlock): a transaction takes row locks only in this order, never an earlier one after a later one: (1) a team's invite advisory lock (`lockTeamInvites`), (2) its `team_invites` row (`FOR UPDATE`), (3) the `teams` row (`FOR NO KEY UPDATE`), (4) the `qbo_connections` row (`FOR NO KEY UPDATE`), (5) `team_members` rows (`FOR SHARE OF tm`), (6) the `users` row (`FOR NO KEY UPDATE`: `lockSessionVersion`, the OAuth exchange, `ensureLocalIdentity`, and the mode any `UPDATE users` takes), (7) `refresh_tokens` rows. The connection paths take 3 → 4 → 5 and never lock `users`. The session paths take 6 → 7: `/refresh` looks up the token's owner, locks the user, then claims the token; a revocation locks the user, bumps it, then deletes its tokens; the OAuth exchange locks the user, then inserts its team and membership; invite accept takes 1 → 2, inserts the membership, then 6 (`setActiveTeam`, `issueSession`). Every state lock is `FOR NO KEY UPDATE`, not `FOR UPDATE`: it conflicts with every other writer of the row (an `UPDATE users SET session_version` takes the same mode, so revocation still serializes with issuance) but not with the `FOR KEY SHARE` a foreign key takes when a job, membership or token row referencing it is inserted, so such an insert never waits on a state lock or closes a cycle. Member removal, suspension and the keepalive's stamps are single statements and hold nothing else. `tests/lock-order.test.js` pins every lock clause in `src` to this table.
- **Disconnecting a sandbox** (`DELETE /connections/:id`, and the admin force-disconnect, both through `services/connection-disconnect.js`: 409 while a pending/running/cancelling job uses it or its lock is held) keeps the `qbo_connections` row: it clears the tokens and sets `disconnected_at`, so the sandbox's jobs keep their `connection_id`. `GET /connections` (and the admin list) show only connected rows and the connection limit counts only those; reconnecting the same realm stores the new tokens on the same row (clearing `disconnected_at`, counted against the limit again), so `has_prior_load` and rollback eligibility survive. Test, health, purge, new QBO jobs and rollbacks refuse a disconnected row with 409 "Reconnect it", and `buildLockedQboClient` throws the same message for any job that reaches one; the token keepalive skips them.
- **Connection health**: `/connections/:id/health` is passive. It does not take the QBO lock or make a QBO network call; it reports age-based status (from `last_used_at`, else `connected_at`) and locally verifies stored token readability so corrupt credentials prompt reconnect before a job starts. A reconnect stores the new tokens with `connected_at = NOW()` and `last_used_at = NULL`, like a new connection, so an expired sandbox is healthy again; it does not take the connection lock (a job still on the old tokens hits a compare-and-swap miss on its next refresh, so the reconnect's tokens win).
- **QBO token encryption**: access/refresh tokens stored AES-256-GCM encrypted in DB with per-row IV (`crypto/tokens.js`)
- **Progress emission**: all long operations (load, purge) accept `emit(step, totalSteps, message)` callback + `AbortSignal`; the worker writes the latest event to `jobs.progress` (at most once a second) and the web app polls it: `useJobs`/`useJob` refetch every 2 s while a job is in `ACTIVE_JOB_STATUSES`
- **Tag-based cleanup**: generated QBO data tagged with prefix (default "EZTD") in PrivateNote/DocNumber for safe purge
- **JWT kinds**: `auth/tokens.js` signs access tokens with `aud=easytestdata:access`, `typ=access` and OAuth state tokens with `aud=easytestdata:oauth-state` + a per-flow `typ`. `authenticate` uses `verifyAccessToken`, so state/other tokens can never be used as access tokens.
- **Proxies / client IP** (Cloud): `TRUST_PROXY` (default off; `1` behind CloudPanel's nginx, or presets like `loopback`) sets Express `trust proxy`; the rate limiter keys on `req.ip`. The nginx vhost restores the client IP from `CF-Connecting-IP` for Cloudflare ranges and overwrites `X-Forwarded-For` (`docs/deploy-cloudpanel.md`). Local mode refuses forwarded requests outright.
- **Logging**: `http/setup.js` `createHttpLogger` redacts `Authorization`/`Cookie`/`Set-Cookie` and strips query strings (tokens live there) from logged URLs and from the `Referer` header (verbose mode logs headers); the error handler does the same, and Sentry errors and transactions go through `scrubSentryEvent` (`beforeSend` and `beforeSendTransaction`: request URL, query string and Referer, plus span and trace URLs and queries).
- **Auth** (Cloud): JWT (15m access / 30d refresh). OAuth issues an ephemeral code exchanged via `POST /api/v1/auth/oauth/exchange`. Sign-in is Google, GitHub or Intuit OAuth only, and nothing sends email. All emails case-normalized via `LOWER(email)`.
- **QBO job fairness**: partial unique index `jobs_one_active_qbo_job_per_team` allows one pending, running or cancelling load/purge/rollback per team; `insertLimitedJob` (`services/job-enqueue.js`) maps it to 409 and applies the monthly load limit to loads only (purges, rollbacks and downloads are never limited). Jobs beyond `QBO_WORKER_CONCURRENCY` wait `pending` and start in order. Cancelling a running job sets `cancelling`; the worker polls, aborts, then sets `cancelled` (the team's QBO slot stays held until then). A failed load can be rolled back once (409 while a rollback is pending/running/completed); a successful rollback is marked completed and its load moved off `failed_with_orphans` in one transaction; a rollback that could not delete every record fails with its report and leaves the load rollback-eligible, so it can be retried.
- **Sessions** (Cloud): refresh tokens are marked `used_at` on rotation; presenting a rotated token again (after a 30 s concurrent-refresh grace) signs the user out everywhere via `revokeUserCredentials`. Access tokens carry `sv` = `users.session_version` and a token without the claim is rejected; `revokeUserCredentials(userId, db?, options?)` (refresh-token reuse, admin revoke-sessions) bumps it and deletes refresh tokens, so tokens issued before the revocation die immediately instead of at expiry. Issuance and revocation are serialized on the users row: both run in a transaction (the caller's client, else one of their own) that first takes `SELECT session_version FROM users WHERE id = $1 FOR NO KEY UPDATE` (`lockSessionVersion`; the mode the revocation's `UPDATE` takes too, so the two conflict and one waits for the other to commit and then sees its generation, while a job insert's foreign-key `KEY SHARE` on the user does not wait; see **Row-lock order**). Every path locks the users row before any token row (`/refresh` looks up the token's owner, locks the user, then claims the token), so it cannot deadlock with a revocation. Every session is issued through `issueSession`: after the lock it compares the current generation with the one the tokens were minted for and `storeRefreshToken` inserts the refresh token with that generation (`refresh_tokens.session_version`) only while `users.session_version` still equals it; a mismatch throws `SessionRevokedError` (401 `SESSION_REVOKED`). `/refresh` refuses (401, token stays consumed) a refresh token whose stored generation differs from `users.session_version`, so a token that slipped past a revocation's delete can never adopt the current generation. `revokeUserCredentials` returns `{ sessionVersion }`; `authenticate` reads the user from the DB on every request, so the bump applies as soon as it commits. Endpoints that mint tokens from an authenticated request (switch-team, invite accept) pass `req.user.sessionVersion` (the `sv` the request authenticated with), so a revocation that lands after `authenticate` can never be turned into a fresh 30-day session (`revokeUserCredentials` also takes `ifSessionVersion` for a guarded revoke). The OAuth callback, `/oauth/exchange` and `/refresh` refuse suspended accounts. The shared web client dedupes concurrent refreshes, re-reads the newest refresh token from localStorage, announces tokens adopted from another tab via `easytestdata:tokens` (`clearTokens` fires it too, so when a rejected refresh clears the tokens `AuthContext` signs out: user, team and query cache cleared), takes the tokens another tab stored or cleared (a `storage` event; announced with `detail.fromOtherTab`, so a signed-out tab signs in, a signed-in one follows the team or account, and a sign-out elsewhere signs out here), and refuses to retry a non-GET request when the refreshed token is for a different user or team (409 `SESSION_CHANGED`).
- **CSV exports**: the admin user export uses `services/csv.js` and the core CSV exporter guards cells too — text starting with `= + - @ \t \r` gets a leading `'` (plain numbers untouched).
- **Admin** (Cloud): one flag, `users.is_admin`. `requireAdmin` (`routes/admin/middleware.js`, 403 unless `req.user.isAdmin === true`) gates the whole admin router, and the users CSV export handler carries it too. The admin area has four views: Overview (counts, trends, server health), Users (list, suspend/unsuspend, sign out everywhere), Jobs (list, detail, cancel, retry, force-fail: a running job whose work runs in this process is aborted (`abortRunningJob`, 202) and failed by the worker's normal path, keeping a load's ledger and the QBO slot until it stops, while a stale running row is failed at once; a retry copies the failed job into its own team with its original creator, `parent_job_id` kept so a rollback retry finds its ledger, through `insertLimitedJob`; a load still in `failed_with_orphans`, or `failed` at its timeout (`result.timedOut`: its work may have gone on after the job was failed), is refused (409 "Roll it back or use 'Remove test data' first") until it is rolled back or a later completed Remove test data on its connection removed its tag or everything, unless the retried config clears first itself (`purgeMode` `generated`, the same tag, or `all`) (`refuseReplayOverOrphans`), since re-running its plan would duplicate every transaction it created) and Connections (health).
- **Limits**: EasyTestData is free. `services/limits.js` applies abuse limits by deployment: Cloud allows 3 connections, 10 loads into QuickBooks per month (`loadsPerMonth`: only `load` jobs count; downloads, purges and rollbacks never do), 5,000 records/job and 5 members per team; local mode is unlimited (-1). The connection limit applies only when the QBO callback would add a new realm (reconnecting an existing sandbox always works; `/connections/authorize` does not check it): `storeConnection` takes the connection-state locks (team row, realm's connection row, membership), then updates the realm or counts and inserts in that transaction, and at the limit redirects with `connection_limit_reached`. Every other limit error is a 403 `LIMIT_EXCEEDED` reading "EasyTestData Cloud allows up to N ... Run it locally for no limits." Monthly usage is derived from the jobs table (`getMonthlyUsage`: this month's loads, counted like the limit counts them, and the sum of this month's completed jobs' `entity_count`); `GET /jobs/usage` returns `{ deployment, limits, usage: { loads, entities } }`, and the Cloud dashboard shows "N of 10 loads this month". Sentry error tracking is optional (`SENTRY_DSN`, `SENTRY_DSN_FRONTEND`).
- **Atomic token consumption**: refresh tokens and OAuth codes use atomic delete-and-return (`take`) or `UPDATE WHERE used_at IS NULL` to prevent replay attacks
- **Team invitations** (Cloud): invites are links to a token-gated `/invite` page; unauthenticated users are redirected to login with the token preserved. Nothing sends email: `POST /teams/:id/invites` always returns `inviteUrl` and the UI shows it with a copy button (re-inviting a pending address rotates the token and resets the invite's role to the one chosen and its expiry to a full 7 days). `DELETE /teams/:id/members/:userId` removes a member (owner: anyone but the owner; admin: members; anyone: themself) and `DELETE /teams/:id/invites/:inviteId` revokes an invite.
- **Active team** (Cloud): `users.active_team_id`. Refresh and the OAuth exchange use it while the user is still a member (`resolveSessionTeam` in `auth/session.js`), else fall back to `ensureTeamForUser` (own/owner team). `POST /api/v1/auth/switch-team { teamId }` (JWT only, membership checked) sets it and returns fresh tokens; accepting an invite switches into the invited team and returns tokens. Web: Settings > Team lists teams with roles and a Switch button (clears the react-query cache, goes to `/home`); `storeTokens` fires `easytestdata:tokens` so `AuthContext` follows team changes.
- **Admin bootstrap**: `ADMIN_EMAILS` (comma-separated, case-insensitive) grants `users.is_admin` at sign-in and at startup (`services/admin-bootstrap.js`, Cloud only). Every stored email was verified by the sign-in provider.

## QBO Sandbox-Only Design

This app is intentionally **sandbox-only** — it should NEVER connect to production QBO. This affects multiple URLs:

- **QBO API**: hard-coded to `https://sandbox-quickbooks.api.intuit.com` (in `connections.js` and the `qbo_connections.base_url` default)
- **Intuit SSO userinfo**: must use `https://sandbox-accounts.platform.intuit.com/v1/openid_connect/userinfo` (NOT the production `accounts.platform.intuit.com` URL — development keys return 403 on the production endpoint)
- **Auth/token endpoints**: `https://oauth.platform.intuit.com/oauth2/v1/tokens/bearer` and `https://appcenter.intuit.com/connect/oauth2` are shared between sandbox and production

The `IntuitSSOStrategy` defaults to `sandbox: true`. If production support is ever needed, pass `sandbox: false` in the strategy options.

## Auth Flows

### Local mode

No sign-in. `authenticate` makes every request the built-in local user (owner of the local team);
`localRequestGuards` is what keeps other sites out. The auth router mounts only `/profile`. The
web app skips all sign-in screens. The QBO connect flow is the same as in Cloud (signed,
browser-bound, single-use state).

### OAuth Login (Google, GitHub, Intuit) — Cloud

1. `/api/v1/auth/:provider` → redirect to provider with signed state. The state is bound to the browser (httpOnly SameSite=Lax cookie `eztd_oauth_login` holding the state's nonce; `Secure` only when `APP_URL` is https, since local mode runs `NODE_ENV=production` over http://localhost and Safari drops Secure cookies there) and single-use (`oauthStates.take` in `state/memory.js`, process memory); see `auth/oauth-state.js`. The QBO connect flow (`/connections/authorize` → `/connections/callback`) uses the same mechanism (`eztd_qbo_connect` cookie) and re-checks, in the transaction that stores the tokens and under the connection-state locks, that the state's user is still an unsuspended member of the state's team. A callback carrying `error` (the user cancelled or declined at the provider) uses up the state and its cookie before anything else and answers `/login?error=oauth_cancelled`, or for the connect flow `connect_cancelled` (popup message or `/home?error=` redirect). A connect callback whose state cannot be used (expired, forgotten by a restart, replayed, from another browser or missing) stores nothing and answers with a page that, since the flow's mode is unknown, messages and closes a popup opened by the app (same-origin opener) and otherwise goes to `/home?error=state_invalid` (or the declined/failed code).
2. Provider callback → `/api/v1/auth/:provider/callback` → passport authenticates → `upsertOAuthUser` (emails normalized to lowercase) → issues ephemeral auth code held in process memory (`oauthCodes`, 2 min TTL, read and deleted in one step via `take`). The code payload is `{ userId, sessionVersion, provider, providerId }` as observed at authentication; `/oauth/exchange` refuses it (400) once the account's `session_version` or OAuth link differs.
   - Returning logins match on (provider, provider id) only. A login links to an existing account by email **only** when the provider asserts the email is verified (Google `email_verified`, GitHub primary+verified from the emails API, Intuit `emailVerified`); otherwise it is refused (`/login?error=oauth_email_unverified`).
   - Every stored email was verified by its provider, so a provider-verified login with the same email as an existing account is attached to it (the account's OAuth link moves to that provider, which also invalidates any unexchanged code for the old link). A new email creates a new account.
3. Redirect to `/login?auth_code=xxx`
4. `LoginPage` picks up `auth_code`, calls `POST /api/v1/auth/oauth/exchange` to swap for JWT tokens
5. `AuthContext` clears any stale tokens from localStorage when `auth_code` is present (prevents loading a previous session's user)

**Important**: The `AuthProvider` init effect checks for `auth_code` in the URL and clears old tokens before fetching any profile. This prevents a race condition where stale session tokens could load the wrong user for an account that wasn't just authenticated.

### New accounts

The first sign-in with a provider-verified email creates the user; its own team (owner membership, active team) is created when the code is exchanged (`resolveSessionTeam` → `ensureTeamForUser`). On EasyTestData Cloud the login page states "By signing in you agree to the Terms" with a link (to `MARKETING_URL`), and nothing about acceptance is stored.

### Team Invite Flow

The invite link is `/invite?token=...`. If unauthenticated, the user is redirected to `/login?invite_token=<token>`; `LoginPage` keeps the token in `sessionStorage` across the provider round trip and, once signed in, redirects back to `/invite`. The `InvitePage` calls `acceptTeamInvite(token)` (`POST /api/v1/teams/invites/accept { token }`: the token travels in the body, never the path, because request URLs are logged), which stores the returned tokens for the invited team (the session switches to it), clears the query cache and redirects to `/settings/team`.
